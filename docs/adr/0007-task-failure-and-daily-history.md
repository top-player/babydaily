# 任务失败状态与每日任务逐日历史

任务新增「失败」这个终止状态：任何任务都能被手动判失败，每日任务还会在 0 点结算时被自动记为失败。

- **每日任务**：当天既没完成、也没手动判失败，0 点结算按 ADR-0004 扣除配置属性后，把这一天记为失败（任务保留，次日照常）。手动判失败时**立即**扣除配置属性并记当天失败——与拖到 0 点的代价一致，避免用"手动失败"逃避惩罚；结算时不会对已判失败的任务重复扣。当天已完成的任务不能判失败，判失败后当天也不能再完成。
- **主线 / 支线**：手动判失败后离开进行中列表，进入「已失败」归档，不发奖、不扣属性，且**是终态**（不提供恢复，只能删除）；失败的主线其子项也不再能勾选完成。
- **每日任务历史**：新表 `DailyTaskLogs` 记录每天每个每日任务的结果（完成 / 失败 + 当天配置的惩罚值快照）。完成与失败都落记录，任务被删除后记录仍保留（快照名称）。
- **每日任务页**：每日任务从任务页拆成独立页面——顶部是今天（可完成 / 可判失败），下方按日期上下滑动查看历史（每次多铺两周，滑到底继续往前加载）；任务页只保留主线/支线/归档，页首卡片显示今天进度并作为入口。

**Considered Options**
- 结算只重置、不记录（原实现）：被否——用户要求"扣除属性后自动记为未完成"，且没有记录就没有历史可看。
- 手动失败不立即扣属性、留给 0 点结算：被否——等于给了逃避惩罚的按钮（用户选择"立即扣除"）。
- 失败的每日任务直接删除或顺延：被否——用户明确要求失败后不删除。
- 主线/支线失败可恢复：被否——用户选择失败是终态（避免"失败→恢复"抹掉记录）。
- 隐藏失败任务（不进归档）：被否——失败也是来时的路，且用户要求保留。

**Consequences**
- 数据库加 `tasks.is_failed / failed_at`（schema v3）与新表 `daily_task_logs`，旧库自动迁移。
- 结算不再惩罚"昨天之后才创建"的每日任务（新任务不在昨天生效，追溯扣分是误伤），这类任务也不写昨天的失败记录。
- 备份 JSON 增加 `tasks.is_failed / failed_at` 与 `daily_task_logs`；版本号仍为 1，导入按增量字段读取，新旧备份都能恢复（老应用导入新备份时忽略新字段）。
